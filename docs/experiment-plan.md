## 1. 프롬프트 5종 설계 원칙

모든 조건은 **system 메시지**로 들어가고, 질문은 **user 메시지**로 들어간다. 대화 이력은 없다(매 요청 단일 턴).

| 조건 | 불확실성 명시 | 자기검증 | 출력 섹션 수 |
|------|:---:|:---:|:---:|
| P0 baseline | X | X | 1 |
| P1 uncertainty | O | X | 1 |
| P2 verification | X | O | 3 |
| P3 combined | O | O | 3 |
| P2L length-control | X | X | 3 |
| P4 prohibition | X | X | 1 |
| P5 few-shot | X | X | 1 |

**통제한 것**
- 첫 두 줄("당신은 한국어로 답변하는 질의응답 어시스턴트입니다 / 사용자의 질문에 답하십시오")은 5종 전부 **글자 단위로 동일**.
- 5종 전부 `[최종답변]` 섹션으로 끝난다. 평가는 **`[최종답변]` 이후 텍스트만** 읽는다. 초안·검토·배경은 저장은 하되 채점에 쓰지 않는다.
- P2L은 P2·P3와 **섹션 수(3개)와 절차 문장 구조가 같다**. 다른 것은 "사실 검토"가 아니라 "재진술 + 배경 설명"이라는 점뿐이다. → 출력이 길어져서 좋아진 것인지, 검증해서 좋아진 것인지 분리된다.

**원안에서 바꾼 것 (중요)**
브리프의 P2 정의는 "불확실한 내용을 수정 또는 **제거**"였다. 그런데 "제거/보류"는 P1(불확실성 명시)의 조작 내용이다. 그대로 두면 P2 안에 P1이 섞여서 **2×2 요인설계가 무너지고 상호작용을 해석할 수 없다.** 그래서 P2는 순수 자기검증("틀린 부분이 있으면 수정")으로만 정의했다. 보류 지시는 P1·P3에만 있다.

**측정 타당도 위험 (논문 제한점에 반드시 쓸 것)**
P1·P3에만 "확인할 수 없습니다"라는 **표현이 지정**되어 있다. 규칙 기반 보류 탐지 사전이 이 표현에 맞춰지면 P0·P2의 보류가 과소 탐지되어 **조건 간 차이가 인위적으로 부풀려진다.** 대응:
1. 보류 표현 사전은 **P0·P2 응답만으로 먼저** 만든 뒤 P1·P3 표현을 추가한다.
2. 규칙에서 미결인 응답은 전부 LLM judge로 넘긴다.
3. 인간 검증 표본을 조건별로 **균등 층화**한다.

### P4 — "환각하지 마라"는 금지 조건 (2×2 밖의 비교군)

**왜 필요한가.** P1은 "확실하지 않으면 확인할 수 없다고 답하라"로, 불확실할 때의 **행동 지침**을 준다. 그런데 실제 사용자가 가장 많이 쓰는 프롬프트는 그것이 아니라 **"지어내지 마"라는 금지**다. 금지는 대안 행동을 지정하지 않는다는 점에서 P1과 다른 조작이며, 지금까지의 설계에는 이 조건이 없었다.

**왜 흥미로운가.** 금지만 하는 지시는 모델에게 실행 가능한 절차를 주지 않으므로, 효과가 없거나 미미할 가능성이 있다. 이것이 데이터로 확인되면 "환각하지 말라고 하면 되는 것 아닌가"라는 소박한 직관에 실험으로 답하는 구조가 된다. 서론에서 던진 질문을 결론에서 회수할 수 있다.

**설계상의 위치.** P4는 **요인이 아니라 비교군**이다. 요인으로 넣으면 2×2×2=8조건이 되어 실행량과 다중비교 부담이 폭증하고, 연구질문 3(상호작용)의 해석도 흐려진다. P2L과 마찬가지로 2×2 밖에 두고 **쌍별 비교**로만 다룬다.
- GEE 요인 분석: P0~P3만 사용 (변경 없음)
- P4: P0 대비(금지의 효과), P1 대비(금지 vs 행동 지침)를 McNemar로 비교, Bonferroni 보정

**문안 원칙.** P4에는 보류 지시("모르겠다고 답하라")도, 검증 절차도 **넣지 않는다**. 넣는 순간 P1이나 P2가 되어 조작이 섞인다. 순수한 금지만 남긴다.

**제한점 (논문에 명시할 것).** P4는 지시문이 P1보다 짧다. 이는 P4가 "짧고 소박한 실제 프롬프트"라는 성격에서 오는 것이라 길이를 억지로 맞추지 않았다. 다만 **입력 프롬프트 길이가 조건 간에 다르다**는 점은 제한점으로 기술한다. (출력 길이 교란은 P2L과 `completion_tokens` 공변량으로 별도 통제한다.)

**파일럿에서 결정할 것.** "환각(hallucination)"이라는 전문용어를 쓸 때와 "사실이 아닌 내용을 지어내지 마십시오"라는 일상어를 쓸 때 모델 반응이 다를 수 있다. 현재 P4 문안은 **둘을 함께** 담고 있다. 파일럿에서 두 표현을 분리해 돌려보고 차이가 크면 본실험에서 P4a/P4b로 나눈다. 차이가 작으면 현행 하나로 간다.

### P5 — 예시만 보여주는 조건 (few-shot, 2×2 밖의 비교군)

**왜 필요한가.** P0~P4는 전부 "어떻게 답하라"는 **지시**다. 그러나 프롬프트 엔지니어링에서 흔히 관찰되는 것은 지시보다 **예시(few-shot)**가 잘 먹힌다는 점이다. 지시 대 예시의 대비가 없으면 "프롬프트 구조"를 다뤘다고 말하기 어렵다.

**예시 3개의 구성.** 목표 행동 세 가지를 각각 한 번씩만 보여준다.
1. 답변 가능한 질문 → 자신 있게 답한다 (물의 화학식)
2. 원리적으로 답할 수 없는 질문 → 보류한다 (2041년 노벨 문학상)
3. 잘못된 전제가 있는 질문 → 전제를 지적한다 (태양이 지구 주위를 도는 주기)

**보류 예시만 넣으면 안 된다.** 보류 예시만 보여주면 모델이 전부 보류하게 되고, 이는 과잉보류를 인위적으로 유발한 것이지 프롬프트 효과가 아니다. 그래서 1번(자신 있게 답하는 예시)이 반드시 들어가야 한다.

**예시 선택의 교란 통제 — 지켜야 할 5가지**
1. 예시는 **모든 질문에 대해 동일**하다. 질문별로 예시를 바꾸면 그것은 프롬프트 조건이 아니라 검색 시스템이다.
2. 예시로 쓴 질문은 **문항 세트에 넣지 않는다.** 겹치면 P5에서만 정답이 프롬프트에 들어 있게 되어 오염이다. → `tools/validate_questions.py`가 자동으로 검사한다.
3. 예시의 **개수(3개)와 순서를 고정**한다. 개수는 입력 길이와 직결되는 통제변인이다.
4. 예시 질문은 **검증이 필요 없는 소재**로 고른다. 미래 사건(정의상 알 수 없음)과 지동설(명백히 거짓인 전제)을 쓴 이유다. 가짜 논문명 같은 것을 예시로 쓰면 그 예시 자체가 실재할 위험이 있다.
5. 예시에 **지시문을 섞지 않는다.** 섞으면 P1이나 P4가 된다. P5는 순수하게 예시만 보여준다.

**설계상의 위치.** P4와 마찬가지로 요인이 아니라 비교군이다.
- GEE 요인 분석: P0~P3만 (변경 없음)
- P5: P0 대비(예시의 효과), P1 대비(**예시 vs 지시**)를 McNemar로 비교, Bonferroni 보정

**제한점 (논문에 명시할 것).** P5는 입력 프롬프트가 다른 조건보다 뚜렷하게 길다(예시 3개). 입력 길이가 조건 간에 다르다는 점, 그리고 예시가 출력 형식까지 보여주므로 `format_ok_rate`가 유리해질 수 있다는 점을 함께 기술한다.

**확장 후보 (본실험에는 넣지 않음)**
- P1-strong: "확실히 아는 것은 답하라"는 문장을 뺀 강한 보류 지시 → 과잉보류 유발 여부 확인
- CoVe: 2턴 이상 분리 호출

## 2. 어떤 AI를 어디에 쓰는가

역할을 섞으면 안 된다. 세 종류다.

### (A) 피험 모델 — 실험 대상, 로컬 3종
| 역할 | 모델 | 이유 |
|------|------|------|
| Main | Qwen3.6-35B-A3B GGUF Q4_K_M (21.2GB, Apache 2.0) | M4 Max 36GB에 들어가는 최대급, MoE라 속도 유리 |
| Replication | Gemma 4 12B (Apache 2.0) | 다른 계열, 연구질문 5(재현성) |
| Platform | gpt-oss-20b MXFP4 (Apache 2.0) | 16GB에 들어가므로 Windows 5070 Ti에서도 **동일 체크포인트** 실행 가능 |

전부 LM Studio + llama.cpp(GGUF) 엔진. thinking OFF 고정.

### (B) 판정 모델(judge) — 채점용, 피험 모델과 겹치면 안 됨
- 피험 3종과 **다른 계열 1종**을 로컬로 띄운다. 후보는 파일럿에서 Cohen's κ로 고른다.
- judge에게는 **질문 + ground_truth + 모델 응답**을 함께 준다. "사실인지 판단하라"가 아니라 **"이 응답이 정답과 일치하는가 / 지어냈는가 / 보류했는가 3분류"**만 시킨다. 판정자가 스스로 사실을 떠올릴 필요가 없으므로 judge 환각 위험이 크게 줄어든다.
- JSON schema 강제 출력, temperature 0, **동일 건 3회 판정 후 다수결**.
- judge는 피험 모델과 **동시에 메모리에 올리지 않는다.** 응답 생성 전량 완료 → 모델 언로드 → judge 로드 → 채점. (36GB에서 21.2GB 모델 두 개는 불가)

### (C) 개발 보조 AI — 코드 작성
Claude(현재 세션). **실험 데이터에는 일절 관여하지 않는다.** 문항 작성·정답 검증·환각 판정에 클라우드 AI를 쓰면 재현성과 오염 통제가 깨진다. 논문에는 "분석 코드 작성에 AI 보조 도구를 사용했으며, 응답 생성 및 채점은 전량 로컬 모델로 수행했다"고 명시한다.

> 문항의 ground_truth와 "존재하지 않음" 확인은 **사람이 출처를 붙여 검증한다.** AI에게 문항을 생성시키면 안 된다 — 존재하지 않는 논문을 AI가 지어내면 그게 곧 채점 기준이 되어버린다. 감점 조건(-2)과도 직결된다.

## 3. 코드 구조

```
hallucination-research/
├── config.yaml                 # 모든 통제변인의 유일한 출처
├── prompts/                    # P0,P1,P2,P3,P2L (완료)
├── data/
│   ├── questions.csv           # 200문항 (+ pilot_questions.csv 20문항)
│   └── abstention_lexicon.txt  # 파일럿에서 만들고 동결
├── src/
│   ├── client.py               # LM Studio OpenAI 호환 API 래퍼 (재시도/타임아웃)
│   ├── run_experiment.py       # 응답 생성 → results/raw_responses.csv
│   ├── evaluate.py             # 4단계 판정 → results/evaluated.csv
│   ├── analyze.py              # 통계 + 그래프 → results/summary.csv, graphs/
│   └── sample_for_human.py     # 인간 검증용 층화 표본 400건 추출
├── results/
└── run_all.py
```

### config.yaml (초안)
```yaml
run_id: pilot_001
server: {base_url: "http://localhost:1234/v1", timeout_s: 180, max_retries: 3}
generation:
  temperature: 0.7
  top_p: 0.9
  top_k: 40
  repeat_penalty: 1.0
  max_tokens: 512
  context_length: 8192
  thinking: false
repeats: 3
seeds: [1, 2, 3]          # 반복마다 seed만 변경
conditions: [P0, P1, P2, P3, P2L]
models:
  - {key: qwen35,   lms_id: "...", quant: Q4_K_M, engine: llama.cpp}
  - {key: gemma4,   lms_id: "...", quant: Q4_K_M, engine: llama.cpp}
  - {key: gptoss20, lms_id: "...", quant: MXFP4,  engine: llama.cpp}
judge: {key: "...", temperature: 0.0, votes: 3}
```

### raw_responses.csv 컬럼
`run_id, question_id, question_type, answerable, question, context, ground_truth,
model_key, model_file_sha256, quant, engine, prompt_type, repeat, seed,
temperature, top_p, max_tokens, response_raw, response_final, prompt_tokens,
completion_tokens, latency_ms, finish_reason, format_ok, timestamp`

- `response_raw` = 전문, `response_final` = `[최종답변]` 이후만 파싱
- `format_ok` = 섹션 파싱 성공 여부. **파싱 실패율은 조건별로 보고해야 한다** — P2/P3에서만 형식을 자주 어기면 그 자체가 결과다
- `completion_tokens` = §1의 길이 교란을 검증하는 공변량

### evaluated.csv 추가 컬럼
`label(CORRECT|HALLUCINATION|ABSTAIN), decided_by(rule|match|judge), judge_votes,
judge_confidence, human_label, human_rater_id`

### 실행 원칙
- **중단 재개(resume)**: 매 응답 즉시 CSV append + `(model, prompt, question, repeat)` 키로 기존 완료분 skip. 12~24시간 배치라 필수.
- **결정 순서 고정**: 질문 순서·조건 순서를 config에 박아 통제변인으로 만든다.
- **모델당 1회 로드**: 모델 루프가 가장 바깥. 모델 스와핑은 시간 낭비.
- `run_all.py` = run_experiment → evaluate → analyze 순차 호출뿐. 로직 없음.

## 4. 지금(맥 없이) 할 수 있는 순서

1. **프롬프트 5종 확정** ← 완료, 검토 필요
2. **파일럿 문항 20개 작성** — answerable 10 / unanswerable 10, 출처 URL 포함. 사람 손으로.
3. **questions.csv 스키마 확정** + 20문항 입력
4. **코드 작성** (`client.py` → `run_experiment.py` → `evaluate.py` → `analyze.py`)
   - LM Studio 없이도 **mock 서버**로 전 구간 테스트 가능. 가짜 응답을 넣어 파싱·채점·통계·그래프까지 끝까지 돌려본다.
5. 맥 확보 후: 모델 다운로드 → 파일럿 100응답 → 보류 사전 구축 → judge 선정(κ) → 본세트 200문항 → 본실험

4번의 mock 테스트가 핵심이다. 실험 당일에 파싱 버그가 나오면 12시간을 날린다.
